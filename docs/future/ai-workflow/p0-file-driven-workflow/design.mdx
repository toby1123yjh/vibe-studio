以下定义当前实现契约，实际完成证明以实施计划中的验证结果为准。历史代码中的 Issue 在本次统一称为“业务任务”，不因此新增对象。

## 1. 对象与职责

### 1.1 业务任务与工作流子任务不是一回事

| 对象             | 含义                                             | 放在哪里                                         |
| ---------------- | ------------------------------------------------ | ------------------------------------------------ |
| 业务任务         | 用户在 VB 中管理的整件事，例如“完成行业研究报告” | 现有项目任务体系；项目文件继续是业务任务内容来源 |
| WorkflowInstance | 这个业务任务使用的工作流实例，与业务任务一对一   | 沿用现有实例模型，不增加第二套实例               |
| WorkflowRun      | 一次正式受理的执行、重试或重做                   | Runtime 的持久执行记录                           |
| 工作流子任务     | 某次拆分产生的内部工作项，例如“比较三个竞品”     | 任务文件描述内容；内部记录关联执行状态           |
| NodeExecution    | 某个固定节点的一次实际执行                       | 沿用现有执行模型，关联子任务、会话及 AgentRun    |

**拆出十项子任务，项目看板不会增加十个任务。** 不给这些子任务创建业务 Task/Issue 或业务子任务，不写入 `project.json` 的业务任务列表，不增加项目或工作目录。它们只在工作流内部存在；必要的 Agent 执行记录和内部会话不是业务任务。

### 1.2 谁决定、谁执行

| 角色             | 负责                                                                   | 不负责                                              |
| ---------------- | ---------------------------------------------------------------------- | --------------------------------------------------- |
| 拆分节点         | 阅读需求和材料，产出可执行的子任务说明                                 | 直接启动下游 Agent、创建看板任务                    |
| 主 Agent         | 理解拆分结果、选择固定执行节点、确定分工和顺序、判断重做范围与异常处理 | 绕过 Runtime 启动进程、改写真实状态、修改已冻结流程 |
| 执行节点的 Agent | 读取分配给自己的文件，完成工作，写出成果和交接说明                     | 私自派发下一项任务、把聊天里的“完成”当作执行成功    |
| Runtime          | 校验提交、落实依赖和批次、启动与停止、去重、恢复、记录事实             | 理解业务并自行重新拆题、仅凭文件出现就判成功        |

实例首次持久化受理后，节点、连线、Agent、模型及提示词保持固定。主 Agent 本次分配多少项工作、引用哪些材料，属于运行输入，不是改图。项目仍最多一个活跃工作流运行，但一个运行内部可以并行。

## 2. 一次完整流转

下面的 A、B 和汇总节点都已经存在于画布中；主 Agent 是管理者，不需要额外画一个“调度节点”。

```text
用户需求 + 项目材料
        │ 正式受理，需求落文件
        ▼
拆分节点：读文件 → 写任务清单与任务说明
        │ Runtime 校验，持久保存待分发事件
        ▼
主 Agent：读任务清单 → 写分工文件 → 提交文件路径
        │ Runtime 校验并受理，不能仅凭文件变化启动
        ├───────────────┐
        ▼               ▼
固定执行节点 A       固定执行节点 B
读任务/材料文件      读任务/材料文件
写成果和交接文件     写成果和交接文件
        └───────┬───────┘
                │ Runtime 判断本批次是否可以继续
                ▼
已配置的汇总节点：读成果文件 → 写最终交付
                ▼
页面 / 主会话系统通知 / 外部 API 展示真实状态与成果引用
```

串行时，Runtime 按分工顺序等待前一步成功后再启动下一步。普通工作流不必经过拆分或主 Agent 分发，也应支持“节点 A 写文件 → 节点 B 读文件”的交接。

## 3. F1：把文件交接补到整个工作流

### 3.1 改什么

改造前，`node_context` 从上游执行的 `output_text` 收集内容，提示词模板和工作流 envelope 注入上游正文。现在该入口使用经过校验的需求、交接索引和成果文件引用，见[runner](../../../../crates/server/src/workflow_runtime/runner.rs)与[file_handoff](../../../../crates/server/src/workflow_runtime/file_handoff.rs)。

下游通过准确的文件引用实际读取内容。原生聊天与审计记录继续保留，缺失文件不会回退到旧聊天正文。

### 3.2 怎么交接

1. 正式启动时，将本轮需求写成项目元数据目录中的需求文件，材料保留原项目相对路径。讨论和状态查询不必生成工作文件。
2. 每个产生内容的节点获得本次专属交接文件路径，在其中列明说明文件、成果文件及需要下游注意的事项。
3. Runtime 在真实 Agent 执行结束后读取交接文件，校验来源、必需文件和运行状态。Agent 正常退出但缺少必需交付，应记录交接失败，不能假装下游已就绪。
4. 下游收到自己的工作要求、上游执行身份、文件路径及简短读取指令，再通过原生读文件工具消费实际内容。
5. 最终交付继续指向项目文件。聊天可概述结论，但不能代替约定的报告、分析或其他成果文件。

普通节点完成交接不要求每个 Agent 都拥有工作流管理 MCP。建议由 Runtime 预告交接路径，在终态观察时统一读取；主 Agent 的分工受理则采用第 5 节的显式工具调用。

| 节点/环节             | 文件化内容                                       | 仍走控制协议的内容                                  |
| --------------------- | ------------------------------------------------ | --------------------------------------------------- |
| 普通 Agent / 拆分节点 | 需求、材料、成果、拆分清单、交接说明             | 执行身份、状态、停止与输入请求                      |
| Condition             | 判断所需证据与上游成果；Agent 判断路径实际读文件 | 合法目标节点/分支选择，仍由 Runtime 校验            |
| HumanGate             | 需要审核的说明和成果引用，页面可打开文件         | 批准/拒绝以及准确的待办身份                         |
| Transform             | 从声明文件读取需要转换的内容，将转换结果写出     | 转换参数、错误与执行状态，不必为了转换启动 Agent    |
| Arena                 | 沿用候选/胜出规则，将被选定成果按文件交接        | 选择、应用、停止等既有控制；不因此取消 Git 相关前提 |
| 汇总节点              | 已完成工作的交接说明、成果及最终交付             | 批次是否满足继续条件                                |
| Start / End / 通知    | 有实际业务内容时引用文件                         | 纯控制事件不强制制造空文件                          |

### 3.3 文件放哪里

建议布局如下。尖括号表示运行时分配的标识，不是需要用户填写的目录；只有系统协作文件按执行组织，业务材料和成果不强制搬家。

```text
项目目录/
├─ .vibe-kanban/
│  ├─ project.json                         现有项目与业务任务，不写入拆分子任务
│  └─ workflows/<run-id>/
│     ├─ request.md                       本轮已受理需求
│     ├─ handoffs/<node-execution-id>.json 交接文件索引
│     └─ splits/<split-execution-id>/
│        ├─ tasks.json                    拆分清单：标识、标题、说明文件引用
│        ├─ tasks/<subtask-id>.md          每项任务的说明、材料与交付要求
│        └─ dispatch.json                 主 Agent 给出的分工与阶段顺序
├─ 资料/                                  业务目录示例，不强制命名
└─ 研究报告.md                            业务成果示例，不强制位置
```

这些是现有 Runtime 使用的文件协议；Markdown 写说明、小型 JSON 写可校验索引，Runtime 不解析自由格式 Markdown 来猜任务边界。这种拆分能精确引用任务，同时避免把正文复制到数据库。

| 文件     | 最少需要表达的内容                                            | 谁写                                  |
| -------- | ------------------------------------------------------------- | ------------------------------------- |
| 需求文件 | 已受理的需求和材料位置                                        | 受理服务，来自用户/调用方明确提交     |
| 拆分清单 | 协议版本、来源拆分执行、各项 `subtask_id`、标题、说明文件路径 | 拆分节点                              |
| 任务说明 | 要做什么、读哪些材料、交付什么；必要的前置约束                | 拆分节点                              |
| 分工文件 | 来源批次/清单标识、分阶段的任务到 `node_id` 映射              | 主 Agent                              |
| 交接索引 | 来源执行、交接说明路径、成果路径；删除项与可读文件分开        | 产出节点；非 Agent 转换由对应处理器写 |

文件不授予权限。Runtime 自己核对实例、运行和节点归属，不相信文件自报的身份或成功状态。交接清单中列出的成果，也不自动被算作“Agent 实际修改的文件”。

交接索引只允许 `schema_version`、`run_id`、`node_execution_id`、`summary_path` 和 `artifact_paths` 五个字段。当前执行的身份与准确格式由 Runtime 启动时提供；拆分说明只定义业务工作和成果要求，要求执行者遵循自己的 Runtime 交接协议，不能自行编造后续执行 ID、状态或哈希字段。Runtime 计算实际文件哈希并记录真实完成状态，非法索引明确失败，不静默改成合法成果。

## 4. F2：新增任务拆分节点

### 4.1 配置与产出

新增 `TaskSplitter` 类型，执行方式复用现有 Agent 底座。配置保留节点名称、Agent、模型、拆分提示词；输入来自工作流需求与上游文件。输出协议和系统目录由 VB 提供，用户不必手填复杂路径。

拆分结果至少让后续执行者知道“任务标识、任务名称、读什么、做什么、交付什么”。任务标识在本次已受理拆分结果内稳定；标题只用于展示，不作为唯一身份。空清单、重复标识、缺失说明文件等应给出具体校验错误，不默认为整项业务已完成。

拆分节点不选择并启动执行者。它可以在说明中写业务依赖；主 Agent 阅读后形成结构化分工。工具与日志可以解释拆分过程，但文件才是后续实际消费的内容。

### 4.2 与固定画布接线

建议将拆分节点下游的固定 Agent 节点作为可分配执行者，并在这段已有连线中明确一个汇总出口。出口可以是已有的汇总 Agent、转换节点或 End，不必新增一种汇总节点。

Runtime 验证候选执行者和汇总出口确实属于已冻结的下游关系；不能向图外、上游或无关分支派工。分工只决定任务落到哪个候选节点以及先后顺序，不新增连线。

建议在保存草稿时就校验这一段派工范围：候选节点与出口必须明确，存在多义汇合或冲突触发来源时提示具体连线问题，不能等执行时让主 Agent 猜出口。保存后的范围随实例首次受理一起冻结；这里新增的是固定图上的批次规则，不是允许主 Agent 任意跳过图约束。

这是新增的批次执行语义：拆分完成后，候选节点进入“等分工”，不能再被旧的“上游成功即执行一次”路径抢先启动。批次分工受理后由同一个 Runtime 推进，未分到任务的候选节点只表示本批次未使用，不伪造成功，也不让整个汇总出口提前跳过。复杂嵌套拆分不在本轮展开。

## 5. F3–F4：主 Agent 分工与自动接力

### 5.1 主 Agent 具体做什么

1. 查询当前运行、固定执行节点及其职责，获取已受理拆分结果的路径。
2. 实际阅读任务清单、说明及必要材料，判断哪些可以一起做、哪些必须等待。
3. 写出分工文件，将每项任务映射到固定节点，并组织为执行阶段。
4. 提交分工文件路径和准确的批次身份；等待 Runtime 返回已受理或具体错误。
5. 后续根据真实进度解释情况，按已有权限请求停止、重试或局部重做。文件里的指令不能扩张它的权限。

沿用现有 `workflow_context`、`workflow_get`、`workflow_submit`、`workflow_stop` 和 `workflow_respond` 等能力。建议仅新增一个专门的 `workflow_dispatch` 操作，接收运行/批次、请求去重标识、分工文件路径和来源内容标识；具体签名在实施规划中落实。

分工是推进当前 Run，不是重新调用 `workflow_submit` 创建一个 Run。新操作复用现有作用域校验与服务，不开放任意启动 Node/Session 的通用工具；MCP 就绪检测也需要同步更新，不能只增加工具名却仍按旧六工具能力判断。

### 5.2 自动接力怎么启动

带拆分节点的工作流需要配置主 Agent。无论从页面还是外部 API 启动，正式受理前都应通过已有准备服务建立或校验原主会话绑定；没有合法配置时明确拒绝启动，不等拆分完成后才发现无人接手。首次准备主会话不等于启动 Agent，也不同于主会话删除后偷偷创建替代会话。

Runtime 在确认拆分完成后，持久保存一个“本运行、本拆分执行等待主 Agent 分工”的事件。后台处理器在原主会话可以接受新一轮工作时，使用它已固定的 Agent 配置启动一次系统来源的处理轮次，并给出任务文件路径。

这不是把系统通知伪装成用户输入，也不是向一个已有输入请求随便调用 `SubmitInput`。现有底座没有可以直接等同于“任意开启新一轮”的闲置通道，需要复用并补齐正规的主会话启动入口。

| 情况                                  | 应有行为                                                  |
| ------------------------------------- | --------------------------------------------------------- |
| 原主会话空闲且环境可用                | 领取一次待分发事件，启动分工轮次                          |
| 主 Agent 正在处理用户消息             | 持久等待，不打断、不覆盖用户消息；主会话轮次启动需互斥    |
| 凭据、进程环境或原主会话不可用        | 展示具体待处理/错误原因，不冒称已分工，不创建替代主会话   |
| 普通完成/异常通知、状态查询、打开页面 | 只展示/查询，不因此自动启动 Agent                         |
| 用户停止、迟到分工、重复事件          | 停止检查与领取/受理共同约束；不能重复派发或复活已停止运行 |

自动接力只为已受理运行的这项分发工作提供授权，不扩大为所有结果自动解释或无限自动重试。主 Agent 本轮结束却未提交有效分工时，应留下“分工未完成”的事实，允许处理和重试，不能无限重开模型轮次。

## 6. F5：串行、并行与汇总

### 6.1 用分阶段计划表达顺序

建议用一个简单规则表达两种方式：**阶段之间串行，同一阶段内部并行**。

例如第一阶段同时执行“资料分析”和“竞品比较”，第二阶段执行依赖二者的“形成建议”。纯串行就是每个阶段一项；纯并行就是全部放在一个阶段。无需另建一张动态子任务图。

Runtime 校验任务全部来自本批次、每项恰好分配一次、节点来自固定候选集合，阶段非空且依赖不矛盾。首次受理后固定这份计划；修正未受理文件可以重新提交，不能通过改文件偷偷改变运行中的分工。

同一阶段不能包含必须先后执行的依赖。已有材料在受理时检查可读性；计划由前一阶段生成的成果则先绑定明确的来源子任务，在生产者成功、交接校验通过后才检查并交给消费者。不能要求未来成果在分工前就存在，也不能误用项目中同名的旧文件满足依赖。

### 6.2 一个节点接多项任务

一个固定节点代表配置好的执行能力，不等于只能处理一项工作。每项工作都需有自己的执行记录、文件引用和错误；不能把若干项拼成一次调用后宣称已分别执行。

建议对子任务增加内部会话绑定：不同子任务并行时使用不同会话，同一子任务的后续合法重试引用原绑定；不把两个并发输入写进同一个原生 Agent 会话。节点的 Agent、模型、提示词仍使用冻结配置，不因新会话而改变。

普通非拆分节点继续沿用既有稳定会话规则。子任务执行仍经现有 AgentRunPort；底座需要的内部执行记录不得转化为看板业务任务。实际可同时运行多少项取决于底座/资源，排队要如实展示，不伪装成并行已启动，也不额外限制 Agent 的工作时长。

### 6.3 批次汇总与普通 fan-in 分开

现有逐上游触发、累计 iteration 的 fan-in 不能直接当作“等本批次全部子任务完成”。本次必须明确记录这一批包含哪些工作项，并以它们的准确执行结果判断阶段和汇总出口是否就绪。

正常路径要求全部必需工作成功且交接文件有效，才让汇总出口消费一次批次结果。只有某个执行节点成功一次，不代表这个节点接到的全部子任务都完成。未使用候选节点不计入等待集合；重启和重复完成事件不能再次启动相同汇总。

失败后的继续范围已确认：不停止同一并行阶段中不依赖失败项的其他工作，依赖失败项的后续步骤暂停。用户或主 Agent 可以明确请求部分成果汇总，受理边界见第 9 节。不能在实施时直接沿用旧 `each` 行为或把失败项当成完成项跳过。

### 6.4 共享目录中的写冲突

主 Agent 根据说明和交付位置安排分工，已知会修改同一文件的工作建议分成先后阶段。多个执行者可共享读取材料，各自输出后再汇总。

这只是协作安排，不是文件系统锁。项目只有一个活跃 Run 也不能阻止人工修改或同一 Run 内的冲突；Runtime 不宣称拥有未实现的操作系统沙箱。不能安全并行的工作应串行处理，不强制每项子任务创建 worktree。

## 7. F6：受理、状态、停止与恢复

### 7.1 文件校验与数据库各管什么

文件负责任务正文与成果；数据库保存 Run/NodeExecution、批次关联、分工绑定、文件路径与内容标识、状态、去重、停止及审计。为执行查询保留必要索引，不增加可编辑子任务正文的数据库副本。

建议最少补充三类持久信息，具体合表或分表由实现决定：

- 拆分批次：来源 Run/NodeExecution、任务清单引用、内容标识、分工受理身份。
- 子任务执行关联：批次内标识、说明文件引用、固定 Node、阶段、实际 NodeExecution 与内部会话绑定。真实执行状态沿用 NodeExecution，待分工等状态从批次事实派生。
- 主 Agent 接力事件：原主会话、来源拆分、领取/完成状态、关联的真实 AgentRun 与去重键。

文件操作和数据库不能共用事务。建议先完整写入临时文件，再在同一目录原子发布；Runtime 成功校验后才事务化受理。只有文件但没有受理记录属于未提交内容，不能在重启扫描时擅自启动。

| 校验点               | 行为                                                                        |
| -------------------- | --------------------------------------------------------------------------- |
| 身份、权限、冻结图   | 后端核对实际作用域；主 Agent 不可通过文件指定其他项目/会话                  |
| 路径与文件可读性     | 使用项目相对路径；规范化并检查实际根、符号链接/Windows junction，不允许越界 |
| 完整性与内容绑定     | 校验结构和必需引用；受理记录绑定清单、任务说明、分工文件的内容标识          |
| 重放                 | 相同请求与内容返回原结果；同一去重标识换了内容则拒绝                        |
| 文件在受理后被改写   | 后续执行前检测不一致并报错，不静默切换输入；不回退数据库或聊天正文          |
| 缺失、半写入、旧提交 | 不派发，返回具体文件/字段原因，不让用户只看到笼统的“失败”                   |

控制文件内容校验不是业务文件快照，也不是抵抗本机任意进程篡改的沙箱。材料和成果仍是当前项目文件；无法保证已经运行的 Agent 读过的字节可回滚。历史文件已改变/删除时必须如实说明，不能承诺恢复旧内容。

### 7.2 状态与停止

页面需要区分“待拆分、待分工、排队、执行中、等待人工、停止中、成功、失败、已停止、依赖未满足”等事实；这些展示状态不要求再建一套与 NodeExecution 竞争的状态机。

用户停止时，Runtime 阻止未开始的分工轮次和子任务，向已启动的主 Agent 分工轮次及执行节点请求停止，并等待真实确认。不能顺便取消主会话中无关的用户轮次。

收到停止请求不等于进程已退出。暂时不可达时保留未确认状态和项目占用，不启动替代执行。自然完成与停止竞争要保留真实结果；失败/停止前已经产生的文件和记录也保留。

停止意图在命令失败、输出收尾或进程退出未确认时保持待处理，后台继续重试，不依赖用户再次点击。只有来源执行、主 Agent 接力及 outbox 全部收尾后才标记已完成并释放占用；失败的 outbox 命令仍属于未完成工作。

业务结果、审计完整性和 OS 进程退出分别记录。宿主释放已结束的控制连接后排空输出；自然退出保留协议末尾输出。清理连接不代表新的用户取消，也不重写已经提交的成功或失败。

### 7.3 恢复与重试

| 场景                     | 处理方式                                                                  |
| ------------------------ | ------------------------------------------------------------------------- |
| 分工受理后服务重启       | 根据已受理计划继续，不要求主 Agent 重新随机分工                           |
| 启动请求已发出但响应丢失 | 通过原执行身份核对进程/AgentRun，不凭超时创建第二份                       |
| 拆分完成但自动接力未完成 | 恢复持久事件，先核对既有主 Agent 轮次和分工受理结果                       |
| 单项失败，正式请求重试   | 沿用实例，新增 Run 与实际执行记录，准确引用原拆分项和成功成果，不清空旧行 |
| 仅恢复服务或重放事件     | 沿用原 Run/执行身份，不算一次新的业务重试                                 |
| 用户明确要求重新拆题     | 通过已有重做受理流程产生新执行；不修改旧清单或已开始实例的图              |

重试成功项的成果复用要校验文件仍可用。不能把“历史曾成功”当作当前文件仍存在的证明，也不能伪造一次新的成功执行来填进度。

## 8. F7：页面与交付怎么变化

复用现有工作流栏目、画布、靠右浮动节点配置框和执行详情，不新增一级导航或独立子任务管理系统。本节只定义信息与操作，不在本轮重新设计整套视觉样式。

| 位置           | 调整内容                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------- |
| 节点选择器     | 增加“任务拆分”类型                                                                            |
| 拆分节点配置   | 配置 Agent/模型/拆分要求，显示从现有连线得到的可分配节点与汇总出口；受理后只读                |
| 运行画布       | 拆分节点显示待分工等真实状态，执行节点简要显示“完成几项/总几项”；不把每个子任务膨胀成画布节点 |
| 工作流执行详情 | 查看内部子任务标题、执行节点、状态、输入/成果文件，按需进入对应执行/会话                      |
| 主会话         | 展示真实系统事件与主 Agent 的分工回复，区分系统自动分工轮次和用户消息；普通通知不自动唤醒     |
| 文件与成果区   | 打开交接文件、浏览项目目录、下载当前成果；错误说明指向准确缺失文件                            |

必要操作沿用停止、处理待办、重试/重做；只能操作 Runtime 当前允许的对象。子任务详情可作为精确重试入口，但不借此修改已冻结 Agent 配置或直接启动进程。

部分汇总沿用现有执行详情中的管理操作入口，不另开页面。页面与 API 同时表达执行事实和交付完整性：例如“汇总已完成 · 部分交付”，并列出未完成项和原因；不能因为汇总成功就把整个业务任务标成全部完成。

交付要分清两种清单：

- **交付文件引用**：本次工作希望用户阅读或下游消费的文件，可能包含原有材料，不代表一定由 Agent 修改。
- **Agent 文件变更记录**：有实际写入证据的新增、修改、删除路径。不能把 Agent 自报清单或整个目录的前后差异当作归属证据；覆盖不完整应明示。删除项没有可下载内容。

外部调用仍通过项目目录浏览/上传/下载以及执行查询取得这些信息；同机和网络调用引用相同业务身份，网络调用方不需要读取服务器绝对路径。结果文件列表不取代完整项目目录浏览。

## 9. 失败处理与汇总规则

### 9.1 并行失败处理：已确认

**2026-10-13 用户确认：并行中一项失败，不停止无关任务；依赖它的后续步骤暂停。** 同一并行阶段中不依赖失败项的其他工作仍按已受理计划继续，不因这次失败整批取消。依赖失败项的后续执行及正常汇总保持阻塞，不把失败项跳过后当作全量完成。

保留各项真实结果，向主会话交回异常；仍有子任务执行时不能提前释放项目占用或声称整个运行已结束。主 Agent 在获准处理时根据现场请求重试或结束，不自动伪造成功、无限重试或因异常通知自行唤醒。用户主动停止仍按整次停止的既有规则执行，不能用“无关任务继续”绕过明确停止。

这样不浪费其他 Agent 的工作；失败后仍可能产生部分成果和运行成本。这一取舍已确认，不再作为待选项。

### 9.2 显式部分成果汇总：已确认

**2026-10-13 用户确认：默认等必需任务全部成功；有失败时，允许用户或主 Agent 明确选择“先汇总已完成部分”，但必须标明缺失项，不能显示为全部完成。** 这是正式的部分交付请求，不是把失败当成功跳过，也不是普通失败通知的自动动作。

已确认规则落实为以下设计：

1. **明确受理**：用户从现有管理入口发起，或主 Agent 在已获准的轮次通过管理工具提交。记录请求来源、准确的源 Run/批次与去重标识；查询、通知、文件编辑不产生此请求。
2. **准确材料**：Runtime 生成本次汇总的文件索引，列明可用成果的来源执行、文件引用，以及失败/缺失项和原因。汇总 Agent 实际读取这些文件，在交付正文中说明局限，不能编造未完成部分。
3. **固定范围**：只允许执行原图指定的汇总出口及合法后续处理，不借部分交付增删节点、替换 Agent 或放行无关的失败依赖。缺失项仍保持原始真实状态。
4. **真实状态**：汇总本身成功与原业务全部完成分开表达。建议 API 增加交付完整性及缺失项字段，页面展示“部分交付”；主会话通知和外部结果保持一致。
5. **安全执行**：不因部分交付请求自动取消仍在工作的无关任务，也不与它们并发争用待汇总成果。继续遵守项目占用、真实停止确认和来源文件校验。
6. **保留历史**：建议沿用正式重做受理路径，新建一个只处理汇总范围的 Run，并引用源执行的成功成果及缺失记录；不重开已结束的旧 Run，也不重新拆题。源 Run 仍在执行时沿用等待当前执行结束的队列策略。

失败依赖造成的“后续暂停”不等于新增一个永久等待人工的占用状态。建议当无关工作都已结束、没有可运行步骤或合法人工待办、相关进程已确认退出时，让源 Run 按真实失败事实收尾，保留未执行步骤及原因。显式部分汇总随后通过原项目队列执行；重复请求或重启恢复不产生第二次汇总。

管理入口建议扩展现有 `workflow_submit` 的交付意图，明确区分普通重做与部分汇总，不再新增另一套 MCP/HTTP 服务。Run 的具体状态枚举、完整性字段和数据库布局在实现中落实，但不能改变上述用户可见语义。零份可用成果不能伪装成已交付报告，应明确返回没有可汇总的成果。
