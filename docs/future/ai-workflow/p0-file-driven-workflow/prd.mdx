## 目标与状态

你提出一个完整的业务需求，由预先配置好的多个 Agent 分工完成。它们通过项目里的真实文件交接，主 Agent 理解任务、决定分工和处理异常，Runtime 负责真正执行、等待、停止和恢复。

例如“根据这些材料完成一份行业研究报告”：一个节点先拆出资料分析、竞品比较等子任务，主 Agent 分给合适的执行节点，Runtime 并行推进；后续节点读取分析文件，形成最终报告。用户不需要逐个会话复制材料，也不需要每完成一步再发一句“继续”。这个能力不限定写代码。

本次 P0 已实现并完成定向自动回归及 Codex / Claude Code 的代表性真实联调，于 2026-10-14 按用户确认的完成条件收口。用户不要求追加扩展实机验证；实际命令、证据与未执行场景仍见实施计划，不将未测场景记为测试通过。

返回[总览](./README.mdx)；实现机制见[技术设计](./design.mdx)，执行顺序和验证场景见[实施与验收计划](./implement.mdx)。

## 功能清单与优先级

以下八项构成本次 P0 闭环，不是八套独立系统。主 Agent 管理已有部分基础，不从零重建。

| 编号 | 需要调整的功能         | 本次设计要点                                                           | 完成后能看到什么                              |
| ---- | ---------------------- | ---------------------------------------------------------------------- | --------------------------------------------- |
| F1   | 全流程文件交接         | 普通节点、判断、审核、转换和汇总都按需读取文件，不只改拆分节点         | 不含拆分节点的工作流也能靠文件接力            |
| F2   | 任务拆分节点           | 新增一种 Node，读取材料并输出工作流内部任务清单                        | 能查看每项任务的说明、材料和交付要求          |
| F3   | 主 Agent 管理与分工    | 读取拆分结果，从固定执行节点中分配任务；沿用查询、停止、重试和重做能力 | 主 Agent 能组织工作，而不只是转述状态         |
| F4   | 拆分后的自动接力       | Runtime 持久记录待分发事件，安排原主 Agent 处理                        | 不需要用户手动提醒下一步；停止后不会自己复活  |
| F5   | 串行、并行与汇总       | 按分工计划执行，独立跟踪每项任务，补齐批次完成判断                     | 多项任务真正串并行，汇总不会提前或重复启动    |
| F6   | 可靠执行与恢复         | 文件提交校验、去重、安全停止、重启恢复及精确重试                       | 出错后知道停在哪里，不重复派工、不清空历史    |
| F7   | 工作流内观察与文件交付 | 在现有画布和执行详情呈现子任务、执行者、状态及文件                     | 看得到过程，也能找到、查看和下载成果          |
| F8   | 真实 Agent 闭环验收    | 定向自动测试加实际 CLI 联调                                            | 证明真实 Agent 会读写文件、调用管理能力并交付 |

暂不纳入本轮：动态增删节点、运行中更换 Agent/模型、画布循环、递归拆分、Agent 群聊、通用数据包平台、新的独立子任务管理页面，以及文件 diff/历史快照平台。外部 Chat/嵌入产品单独规划；已有外部 API 继续共用这套运行时，不另造调度器。

## 需求：MR10–MR18

本节为本次已确认需求，具体技术方案见[技术设计](./design.mdx)。MR15 是对原 MR7–MR8 不自动唤醒规则的限定扩展；普通节点的稳定会话规则不被拆分子任务取代，内部子任务并行执行须有独立执行/会话关联，不能向同一个原生会话并发写入多个任务。

- MR10：新增独立的任务拆分节点。该节点读取任务及材料文件并写出任务清单文件，不以聊天正文作为唯一交付。建议每个条目至少包含稳定标识、标题和执行说明，并关联所需材料及交付要求；普通重试或服务恢复复用已受理拆分结果，不重新随机拆分。
- MR11：主 Agent 读取任务拆分节点的结果，为每个任务从工作流中预先配置的执行节点中选择执行者；用户已明确确认固定节点边界。主 Agent 不得临时创建执行节点、修改已冻结的连线或替换节点的 Agent/模型配置。并行/串行均须支持；建议主 Agent 通过受限的工作流管理工具提交分发计划，Runtime 负责校验及实际调度，不由主 Agent 直接写生命周期表或启动底层进程。
- MR12：Runtime 校验主 Agent 的分发请求只引用已受理实例中的合法节点和当前拆分结果，持久化任务项、分配关系、顺序/并行模式及幂等键，然后按策略创建后续执行节点的独立 iteration。每个任务有独立状态、输入、输出、错误和停止结果。
- MR13：并行模式允许多个任务同时运行，但仍遵守项目和实例的现有占用规则；串行模式按确定顺序运行，前置成功且交接有效后才执行依赖它的下一项。单个任务失败、停止或主 Agent 异常不会抹掉其他任务的真实记录。并行中一项失败，不停止同阶段不依赖它的其他任务，依赖失败项的后续步骤和正常汇总保持阻塞；仍有活跃任务时不释放项目占用或冒报整次执行结束。此规则不覆盖用户显式停止，不授权异常通知自动唤醒或无限重试；显式部分汇总见 MR18。
- MR14（已确认）：拆分结果只是工作流内部子任务，不是 VB 的业务任务，不创建项目看板 Task/Issue，也不创建其业务子任务，不向 `project.json` 写入这些业务任务记录。子任务在工作流运行详情内关联对应执行节点、执行记录及文件，不另建项目、工作目录、图节点或任务管理入口。Runtime 可保存必要的内部执行记录和状态；这不等于创建新的业务任务。
- MR15（已确认方向）：拆分完成后，Runtime 自动安排原主 Agent 处理本次运行的待分发事件，无需用户另发消息；普通结果通知、读取结果和打开会话仍不触发 Agent。分发必须先有有效的已受理运行及拆分文件，事件重放不重复分发，停止后不再启动后续任务。主 Agent 不可用时保留待处理状态，不冒报已分发，不创建替代主会话；自动处理不能覆盖或打断用户消息。
- MR16（已确认方向）：任务清单、分工决定、执行说明和成果交接以项目内文件为载体，主 Agent 和执行节点实际读取对应文件。聊天/工具参数只传任务标识、项目相对文件路径及必要简短指令，不把完整任务正文和上游成果拼成提示词替代文件交接。建议用 Markdown 承载任务与交接说明，用小型结构化分工文件承载任务到固定 Node 的绑定和并行/串行顺序；Runtime 验证文件后才受理。文件是任务内容来源，数据库负责运行状态、执行关联、领取/去重、停止和审计，不形成第二套可编辑任务正文。文件存在或声称完成不证明 Agent 成功，文件变化也不自动成为新执行指令。
- MR17（独立 P0，已确认方向）：将“工作流流转尽量使用文件”作为全流程基础改造，补齐已有节点的交接缺口，而非只让拆分节点写文件。普通执行节点、分支判断所需材料、人工审核材料、转换结果和最终汇总涉及任务内容或成果交接时优先引用文件；不以自动拼接全部上游正文作为主要交接方式，也不只是把聊天内容另存备份。短提示、文件路径、控制决策、状态事件及工具调用仍可走现有协议，不把 Start/End、每条通知或心跳强制变成文件，不另建文件轮询调度器。Runtime 继续校验依赖、调度、停止及恢复，数据库继续记录真实运行状态；文件可读不等于依赖已成功，文件改动不自动触发运行。沿用项目目录和现有元数据目录，不强制重排业务文件或新增通用数据包平台。
- MR18（已确认）：正常汇总默认等待必需任务全部成功且交接有效。有失败时，用户或主 Agent 可以明确请求先汇总已完成部分，Runtime 按准确源执行、合法汇总出口和项目队列受理，不因通知或文件变化自动发起。汇总必须实际读取成果文件和缺失项说明；页面、主会话与 API 标明部分交付及局限，不将原失败改成成功，不因汇总节点成功就将业务任务标为全部完成。保持既有停止、占用、去重及历史规则，不为部分交付另建实例或业务任务。

## 沿用的基础约束

- 业务任务与 WorkflowInstance 一对一；一次正式执行、重试或重做使用独立 Run，恢复与重放沿用原执行身份。
- 首次持久化受理后，实例的节点、连线、Agent、模型、提示词固定。调整模板只影响新实例。
- Runtime 是唯一调度方；主 Agent 通过受限管理能力提交意图，页面、MCP 与外部 HTTP 共用业务服务。
- 同项目最多一个活跃工作流 Run，内部可以并行；停止未确认、仍有子执行时不释放项目占用。
- 拆分结果只在工作流内部管理；业务材料和成果位置自由，不按业务任务或执行次数强制分目录。
- 原主会话删除后不补建替代会话，普通通知不自动启动 Agent。MR15 只为已受理拆分的待分发事件扩展自动接力。
- Agent 文件变更只记录有归属证据的路径和新增/修改/删除类型，不提供 diff、历史字节快照或系统级全量追踪；目录浏览仍是完整项目文件入口。

此前的架构与实现事实见[运行时控制设计（历史基线）](../runtime-control-design.md)。本次新增或扩展规则以本目录为准，历史验收欠项保持独立。

## 验收标准：MAC9–MAC15

MAC9–MAC15 按 2026-10-14 用户确认的完成条件收口：功能实现、定向自动回归及 Codex / Claude Code 核心真实联调已完成。MAC10、MAC14–MAC15 的扩展实机场景不再作为本任务的完成条件；勾选表示按上述范围完成，不表示所有故障场景均已实测。逐项实际覆盖见下表和[实施记录](./implement.mdx)。

- [x] MAC9（MR10–12、MR16）：拆分节点真实写出任务文件，主 Agent 读取后写出分工文件；后续节点按任务 ID 读取文件而非接收全部上游正文。文件缺失、未写完整、路径越界或包含非法执行节点时不得派发，也不回退到聊天或数据库的旧正文继续执行。
- [x] MAC10（MR15）：有效拆分提交无需用户追加消息即可触发主 Agent 分发；普通通知、查询和打开会话不触发。重放/重启不重复分发，停止与自动接力竞争不复活任务，主 Agent 不可用显示真实等待状态。
- [x] MAC11（MR13–14、MR16）：串行/并行执行均能定位每项任务文件、分工决定、独立执行状态和交付文件；修改文件中的状态文字不能伪造成功，不要求把所有业务成果搬到固定 inputs/outputs 目录。
- [x] MAC12（MR17）：不含拆分节点的普通两节点工作流也能由上游写文件、下游按引用读文件并完成交付，启动提示不包含整段上游成果副本。对既有各类内容交接验证文件引用路径；必要文件缺失/不可读不能退回旧聊天正文假装可执行，只有文件而无真实依赖成功不能推进，纯控制事件无需制造空文件。
- [x] MAC13（MR14）：拆分、分发、重试及恢复均不增加 VB 看板业务任务或业务子任务，不改变项目业务任务清单来表示拆分结果；工作流内部仍能独立追踪各子任务、执行者、状态和成果文件。
- [x] MAC14（MR13）：并行 A/B 中 A 失败时，B 不因该失败被取消并能保留真实结果，依赖 A 的后续节点和正常汇总不启动；B 尚未结束时保留项目占用。用户明确停止仍会安全停止未完成工作；恢复后不能丢失失败依赖或将其当作成功跳过。
- [x] MAC15（MR18）：无明确请求时不做部分汇总；用户或主 Agent 提交后，引用准确的成功成果和失败/缺失清单，输出与页面/API/主会话均表明部分交付，保留原失败和业务任务真实状态。仍有无关工作执行时不自动取消或抢占；源运行收尾后依原队列执行，重放与服务重启不重复受理或启动；零份可用成果、引用失效或越权时明确报错，不伪装交付成功。

| MAC10 | 持久接力、恢复去重、停止竞争及忙/不可用             | 无需追加用户消息的原主会话 System 分工；真实重启/用户轮次竞争未测      |

## 风险与验证原则

- 文件与数据库不能共享事务，必须验证部分写入、内容变更、幂等受理和恢复，不能仅凭文件出现推进流程。
- 旧逐上游触发与新批次调度不能同时启动同一工作；不同子任务不能向同一原生会话并发输入。
- 自动分工与用户消息、停止、服务重启可能竞争，必须保留准确执行身份与真实状态。
- 部分汇总不能清除失败事实，也不能因失败依赖造成永久占用。
- 共享目录不是文件锁或进程沙箱，不能保证人工写入或多个 Agent 写入互不冲突。
- 自动测试与真实 CLI 验收分开记录。至少验证 Codex、Claude Code；未测 provider 和原 HTTP/异机验收不能冒称通过。
